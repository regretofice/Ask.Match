# 1. US-08

**标题**

```
[US-08] 报名后能看到"已提交 / 已接受 / 已确认"哪一档
```

**编号**：US-08

**用户故事**

> 作为已报名的参与者，我想看到自己处于"已提交 / 已接受 / 已确认"中的哪一档，以便判断这次到底算不算约好、还要不要再问一遍。

**验收标准**

- Given 我已提交申请且发起者尚未处理，When 我打开活动详情，Then 状态显示"已提交"，并提示"尚未确认，请勿按已确认安排行程"。
- Given 发起者已接受我的申请，When 我再次打开详情，Then 状态显示"已确认"，并显示时间、地点与取消入口。
- Given 活动时间被修改，When 我尚未重新确认，Then 状态回退为"待重新确认"，不显示为"已确认"。
- Given 我已在约定时间到达现场，When 我打开详情，Then 可将状态标记为"已到场"（仅作记录，不改变名单）。

**证据**

- [S01 Q07](https://github.com/regretofice/Ask.Match/blob/main/doc/调研报告/有问必搭_调研回答整理.md#L29)：时间和地点确定后通常算约好
- [S05 Q07](https://github.com/regretofice/Ask.Match/blob/main/doc/调研报告/有问必搭_调研回答整理_S05-S09.md#L44)：最明确的信号是"你参与了这个活动的讨论"
- [S06 Q07](https://github.com/regretofice/Ask.Match/blob/main/doc/调研报告/有问必搭_调研回答整理_S05-S09.md#L65)："来到现场我才知道已经约好"
- [S09 Q07](https://github.com/regretofice/Ask.Match/blob/main/doc/调研报告/有问必搭_调研回答整理_S05-S09.md#L125)：把"已经提前 AA 钱"也算作承诺
- [S01–S04 归纳#2](https://github.com/regretofice/Ask.Match/blob/main/doc/调研报告/有问必搭_调研回答整理.md#L84)：至少五种状态需要区分（已邀请/已接受/已确认/已到场/已付费）

**证据强度**：强（4 位受访者亲身经历，且判断标准互相冲突）

**干系人**：参与者 / 发起者

**优先级**：P0

理由：这是本项目最独特的痛点。微信和校园墙都没有状态机，用户只能靠"再问一遍"确认，而这正是 S05、S07、S08 反复提到的摩擦；也是期末答辩追溯链的样板条目。

**待决问题**

1. "已付费"是否作为独立状态？涉及 AA 与退款规则。
2. "已到场"由谁标记（本人 / 发起者 / 系统）？标记错误能否撤销？
3. 时间变更后"待重新确认"的有效期多长？过期是否自动移出名单？

**关联用例**：UC-02、UC-03

# 2. US-09

**标题**

```
[US-09] 名额满后自动转候补并按顺序递补
```

**编号**：US-09

**用户故事**

> 作为发起者，我想在名额满后把后来的申请转为候补并按顺序递补，以便有人退出时能自动补上，而不用重新发帖找人。

**验收标准**

- Given 名额 6 人且已确认 6 人，When 第 7 人提交申请，Then 其状态显示"候补·第 1 位"，不占用名额，且发起者能看到完整候补队列。
- Given 候补队列有 2 人，When 1 名已确认者退出，Then 候补第 1 位在 1 分钟内收到"有空位"通知并进入"待确认"，其余候补顺序不变。
- Given 候补者未在发起者设定的时限内响应，When 时限到达，Then 系统自动顺延给下一位，并通知发起者已顺延。
- Given 活动被标记为"正式活动"，When 发生递补，Then 系统提示"距开始不足 24 小时，替补可能来不及准备"，由发起者决定是否仍递补。

**证据**

- [S06 补充（S02 场景）](https://github.com/regretofice/Ask.Match/blob/main/doc/调研报告/有问必搭_调研回答整理_S05-S09.md#L72)：空位应"全体通知"；正式活动替补至少提前一天，娱乐活动随意
- [S01 Q08](https://github.com/regretofice/Ask.Match/blob/main/doc/调研报告/有问必搭_调研回答整理.md#L30)：运动会组队有人退出，靠学工老师和熟人找替补，条件逐步放宽
- [S02 Q08](https://github.com/regretofice/Ask.Match/blob/main/doc/调研报告/有问必搭_调研回答整理.md#L45)（反向）：人数通常够用，很少重新找人

**证据强度**：中（1 位亲身经历 + 1 位规则设想；S02 的反向证据说明候补不是高频需求）

**干系人**：发起者 / 参与者

**优先级**：P1

理由：真实需求存在但频率低（S02 明确说很少补人），且实现依赖 US-08 的状态机。不做不会直接导致答辩失分，但会丢掉"名额可信"的完整闭环。

**待决问题**

1. 候补响应时限：30 分钟 / 2 小时 / 发起者自定？
2. "正式活动提前一天"与"有人退出立即递补"冲突时，以哪个为准？
3. 候补者能否同时排多个活动的候补？

**关联用例**：UC-03

# 3. US-10

**标题**

```
[US-10] 候补者收到空位通知后能确认补位
```

**编号**：US-10

**用户故事**

> 作为候补者，我想在有空位时被通知并能确认是否补位，以便不错过机会，也知道补位后要准备什么。

**验收标准**

- Given 我是候补第 1 位，When 有人退出产生空位，Then 我在 1 分钟内收到站内 + 推送通知，状态变为"待确认"。
- Given 我收到补位通知，When 我确认参加，Then 状态变为"已确认"，并显示最新的时间、地点与集合方式。
- Given 我收到补位通知，When 我选择放弃，Then 状态回到候补队尾或移出队列，并立即顺延给下一位。
- Given 活动在 24 小时内开始，When 我被通知补位，Then 通知中明确写出"距开始 X 小时"，由我判断是否来得及。

**证据**

- [S06 补充（S02 场景）](https://github.com/regretofice/Ask.Match/blob/main/doc/调研报告/有问必搭_调研回答整理_S05-S09.md#L72)：空位应全体通知；替补时限与活动性质相关
- [S09 Q07](https://github.com/regretofice/Ask.Match/blob/main/doc/调研报告/有问必搭_调研回答整理_S05-S09.md#L125)：已付费也算承诺 → 补位可能涉及补交费用
- [S09 Q08](https://github.com/regretofice/Ask.Match/blob/main/doc/调研报告/有问必搭_调研回答整理_S05-S09.md#L126)：退出时先看能否拼接双方计划，不行才按退出处理

**证据强度**：中（由候补流程推导，1 位受访者的规则设想 + 1 位退出经历）

**干系人**：参与者 / 发起者

**优先级**：P1

理由：与 US-09 同一闭环。单独看价值不大，但缺了它，"自动递补"没有落点，US-09 也无法验收。

**待决问题**

1. 补位后 AA 费用如何结算？已付费者的退款顺序？
2. 放弃补位是否计入"爽约"？与 US-25 的判定口径需要对齐。

**关联用例**：UC-03

# 4. US-11

**标题**

```
[US-11] 报名时提示"名单里有我不想见的人"
```

**编号**：US-11

**用户故事**

> 作为参与者，我想在报名时被告知名单里有我不想再见的人，以便决定是否仍参加，而不是到场才发现。

**验收标准**

- Given 我已把某人加入屏蔽名单，When 我打开该人已确认参加的活动详情，Then 报名前提示"名单中有你屏蔽的人"，且不显示对方姓名。
- Given 我收到该提示，When 我选择继续报名，Then 报名正常提交，双方都看不到彼此的屏蔽关系。
- Given 我是活动发起者，When 我审批申请，Then 我看不到申请者与他人之间的屏蔽关系，避免据此拒绝。

**证据**

- [S05 补充](https://github.com/regretofice/Ask.Match/blob/main/doc/调研报告/有问必搭_调研回答整理_S05-S09.md#L50)：想拉黑又觉得不好；希望报名时提示"有我拉黑的人已确认报名"并再次确认
- [S09 补充](https://github.com/regretofice/Ask.Match/blob/main/doc/调研报告/有问必搭_调研回答整理_S05-S09.md#L131)：希望有黑名单；且提醒同时发给组织活动的第三人
- [S03 Q09](https://github.com/regretofice/Ask.Match/blob/main/doc/调研报告/有问必搭_调研回答整理.md#L61)：提到"自己难以接受的人"

**证据强度**：弱（两位受访者的设想，未在真实场景中使用；S05 自己说"拉黑不太好"，态度摇摆）

**干系人**：参与者 / 发起者

**优先级**：P2

理由：证据弱、涉及隐私与歧视风险，且实现成本不低（需要屏蔽关系模型）。本轮只做记录与设计讨论，不排开发。

**待决问题**

1. 提醒范围：只提醒自己，还是也提醒组织者？S05 与 S09 意见不一致。
2. 被屏蔽者能否申请同一活动？申请后是否通知双方？
3. 屏蔽关系是否对第三方可见？会不会变成"站队"工具？
4. 与举报（US-23）的边界在哪？

**关联用例**：UC-02、UC-03

# 5. US-25

**标题**

```
[US-25] 多次无故爽约的分级处置与申诉
```

**编号**：US-25

**用户故事**

> 作为运营管理员，我想对多次无故爽约的用户分级处置（提醒 → 警告 → 限制）并保留申诉，以便既约束行为，又不误伤确实有临时情况的人。

**验收标准**

- Given 用户 A 在 30 天内被 3 位不同发起者标记"无故爽约"，When 达到阈值，Then 系统只生成待处理项，不自动处罚。
- Given 运营者核实后判定成立，When 执行处置，Then 第一次为站内提醒，第二次为警告并限制 7 天内报名，第三次限制 30 天。
- Given 用户认为处置有误，When 提交申诉，Then 运营者在 48 小时内复核，复核期间限制不升级。
- Given 用户提供了"临时突发情况"说明且经发起者确认，When 核实，Then 不计入爽约次数。

**证据**

- [O01 问题二](https://github.com/regretofice/Ask.Match/blob/main/doc/调研报告/有问必搭_运营管理员访谈记录.md#L24)：要举报与反馈渠道；按情节警告，情节严重限制账号；"不能一概而论"（此链接需分支合并后生效）
- [S06 补充（平台滥用）](https://github.com/regretofice/Ask.Match/blob/main/doc/调研报告/有问必搭_调研回答整理_S05-S09.md#L73)：主张实名并公开活动记录，但认为规则总会被钻空子
- [S05 补充](https://github.com/regretofice/Ask.Match/blob/main/doc/调研报告/有问必搭_调研回答整理_S05-S09.md#L50)：屏蔽与婉拒的诉求，是处置的另一面

**证据强度**：中（角色当事人陈述，但样本量 1，无实际处置数据）

**干系人**：运营管理员 / 参与者 / 发起者

**优先级**：P2

理由：涉及处罚，是全部条目里风险最高的一条；且依赖 US-23 积累举报数据，MVP 阶段没有足够样本触发阈值。本轮只写清规则，不排开发。

**待决问题**

1. 阈值：30 天 3 次是否合理？不同类型活动是否分开计？
2. 谁举证："无故"由发起者标记，还是系统按"已确认未到场"自动判定？
3. 申诉由谁复核？学生运营者既执行又裁判，是否需要两人复核机制？
4. 被限制期间，已确认的活动是否强制退出？

**关联用例**：UC-10

# 6. NFR-01

**标题**

```
[NFR-01] 抢名额时不超发、2 秒内返回
```

**编号**：NFR-01

**用户故事**

> 作为参与者，我想在热门活动开放报名时提交申请能立刻得到结果，以便知道自己是第几个，而不是刷新半天还不确定。

**验收标准**

- Given 同一活动 200 人同时提交申请、名额剩 10，When 并发提交，Then 95% 请求在 2 秒内返回，且确认人数严格不超过 10。
- Given 名额刚好被抢完，When 第 11 人提交，Then 直接进入候补并收到明确提示，不出现"提交成功但没位置"。
- Given 系统处于高峰，When 请求排队，Then 用户看到"排队中·第 N 位"，而不是超时失败或白屏。
- Given 某次提交因网络异常重试，When 恢复，Then 同一申请不产生重复记录（与 NFR-03 联动）。

**证据**

- [S06 补充（S02 场景）](https://github.com/regretofice/Ask.Match/blob/main/doc/调研报告/有问必搭_调研回答整理_S05-S09.md#L72)：满员时应"全体通知"，说明满员是高频状态
- [S09 Q07](https://github.com/regretofice/Ask.Match/blob/main/doc/调研报告/有问必搭_调研回答整理_S05-S09.md#L125)：已付 AA 钱也算承诺 → 超发会造成"有人付了钱没位置"的真实损失
- 课堂示例（200 并发）：**团队技术假设，不是用户要求**

**证据强度**：中（由用户行为推导 + 团队技术假设，无真实并发数据）

**干系人**：参与者 / 发起者

**优先级**：P0

理由：这是唯一"出错就产生真实损失"的场景（有人付了钱、有人白跑一趟），也是老师必问的非功能项。答辩时能拿出可测的验收标准，比写十个功能都管用。

**待决问题**

1. 200 并发是课堂举例，真实峰值需按活动规模估算，不能当成用户要求。
2. 超发时如何裁决：先到先得 / 抽签 / 发起者手动定？
3. 排队机制是否过度设计？MVP 可先只做"超时重试"。

**关联用例**：UC-03

# 7. NFR-02

**标题**

```
[NFR-02] 未确认前联系方式绝对不可见，越权访问留痕
```

**编号**：NFR-02

**用户故事**

> 作为参与者，我想在双方确认之前，任何人（包括未登录用户和直接调接口的人）都拿不到我的联系方式，以便放心报名，不用担心资料被爬走。

**验收标准**

- Given 我把联系方式设为"仅双方确认后可见"，When 一名尚未确认的同学打开我的资料，Then 页面与接口都不返回该字段（是不下发，不是前端隐藏）。
- Given 我把联系方式设为"公开"，When 一名尚未确认的同学查看，Then 仍然不可见 —— 未确认状态下的最小门槛由系统固定，不随用户设置改变。
- Given 任意账号，When 在 1 分钟内请求用户资料超过 60 次，Then 被限流并返回 429，且记入审计日志。
- Given 我完成学号或校园邮箱认证，When 他人查看我的主页，Then 只显示"已认证"徽章，不显示学号、邮箱原文。
- Given 运营者处理举报，When 其查看用户完整联系方式，Then 需二次授权，且操作写入审计日志（谁、何时、看了谁、理由）。

**证据**

- [S03 Q09](https://github.com/regretofice/Ask.Match/blob/main/doc/调研报告/有问必搭_调研回答整理.md#L61)：愿意公开的只有部分信息，"其他不太愿意"
- [S09 Q09](https://github.com/regretofice/Ask.Match/blob/main/doc/调研报告/有问必搭_调研回答整理_S05-S09.md#L127)：愿意给不认识的人看的"只有个人信息"
- [S05 Q09](https://github.com/regretofice/Ask.Match/blob/main/doc/调研报告/有问必搭_调研回答整理_S05-S09.md#L46)：愿意公开的是社交平台上已经展示的信息
- [S08 Q09](https://github.com/regretofice/Ask.Match/blob/main/doc/调研报告/有问必搭_调研回答整理_S05-S09.md#L107)：取决于好友转述了什么，自己"也没有什么特别隐私的东西"
- [O01 问题一](https://github.com/regretofice/Ask.Match/blob/main/doc/调研报告/有问必搭_运营管理员访谈记录.md#L18)：建议学号或校园邮箱认证 —— 认证徽章与"原文不外显"的依据（此链接需分支合并后生效）
- [O01 问题三](https://github.com/regretofice/Ask.Match/blob/main/doc/调研报告/有问必搭_运营管理员访谈记录.md#L30)：统一后台查看用户信息 —— 运营者权限与审计的依据（同上）
