# 用户故事 Issue 填写模板

- 用途：组员**照着这一条写**，格式就不会散
- 适用：第 02 课课后任务（Issue 化）→ 第 03 课开课检查
- 关系说明：`.github/ISSUE_TEMPLATE/user-story.yml` 管**字段**，本文管**写法**

---

## 一、三步提交

1. 打开仓库 `Issues → New issue`
2. 有「用户故事 / 非功能需求」表单就用表单；**表单还没合并到 main 时，选「Open a blank issue」**，把下面「空白骨架」整段粘进去
3. 提交后：**Assign 自己** → 打 `story`（或 `nfr`）+ `P0/P1/P2` + `area-*` → 回 `用户故事清单.md` 把状态改成 `已核对·你的名字`

---

## 二、空白骨架（复制这段）

```markdown
## 编号
US-xx

## 用户故事
作为〈角色〉，我想〈做什么〉，以便〈得到什么价值〉。

## 验收标准
- Given 〈前提〉，When 〈动作〉，Then 〈可观察的结果〉。
- Given 〈前提〉，When 〈动作〉，Then 〈可观察的结果〉。

## 证据
- [Sxx Qxx](doc/调研报告/文件名.md#L行号)：这条证据说了什么
- [Sxx Qxx](doc/调研报告/文件名.md#L行号)：这条证据说了什么

## 证据强度
强 / 中 / 弱

## 干系人
参与者 / 发起者 / 运营管理员 / 付费方（活动 AA）

## 优先级
P0 / P1 / P2 —— 理由：〈频率 / 影响 / 有无替代办法〉

## 待决问题
〈评审要吵的点，没有就写"无"〉

## 关联用例
UC-xx
```

## 三、完整样例（US-08，照着这个写）

> 这是全组最好的一条，也是期末答辩追溯链的样板。你写的时候不必有 3 组验收标准，
> 但**结构必须和它一样**。
>
> 注意链接写法：Issue 正文里的相对链接是按**仓库根目录**解析的，所以写 `doc/调研报告/xxx.md#L44`，
> 不要写 `../调研报告/...`——后者是本地文件互链的写法，贴进 Issue 会点不开。

### 标题

```
[US-08] 报名后能看到"已提交 / 已接受 / 已确认"哪一档
```

### 正文

```markdown
## 编号
US-08

## 用户故事
作为已报名的参与者，我想看到自己处于"已提交 / 已接受 / 已确认"中的哪一档，
以便判断这次到底算不算约好、还要不要再问一遍。

## 验收标准
- Given 我已提交申请且发起者尚未处理，When 我打开活动详情，
  Then 状态显示"已提交"，并提示"尚未确认，请勿按已确认安排行程"。
- Given 发起者已接受我的申请，When 我再次打开详情，
  Then 状态显示"已确认"，并显示活动时间、地点与取消入口。
- Given 活动时间被修改，When 我尚未重新确认，
  Then 状态回退为"待重新确认"，不显示为"已确认"。

## 证据
- [S05 Q07](doc/调研报告/有问必搭_调研回答整理_S05-S09.md#L44)：最明确的信号是"你参与了这个活动的讨论"
- [S06 Q07](doc/调研报告/有问必搭_调研回答整理_S05-S09.md#L65)："来到现场我才知道已经约好"
- [S09 Q07](doc/调研报告/有问必搭_调研回答整理_S05-S09.md#L125)：把"已经提前 AA 钱"也算作承诺
→ 三种判断标准互相冲突，说明"算不算约好"没有共识

## 证据强度
强（3 位受访者亲身经历，且判断标准互相冲突）

## 干系人
参与者 / 发起者

## 优先级
P0 —— 理由：这是本项目最独特的痛点，现有工具（微信群、校园墙）都没有解决

## 待决问题
"已付费"是否应作为独立状态？需与名额规则、AA 规则一起评审。

## 关联用例
UC-02、UC-03
```

## 四、四条硬规则（违反任何一条都会被退）

| 规则                   | 说明                                       | 反例                                           |
| ---------------------- | ------------------------------------------ | ---------------------------------------------- |
| **三段式缺一不可**     | 作为〈角色〉、我想〈做什么〉、以便〈价值〉 | "作为学生，我想搜索课程"——缺"以便"，价值说不清 |
| **验收标准必须能打勾** | 看得见、量得出                             | "界面友好""响应要快"——没法检验                 |
| **证据必须点得开**     | 行号链接，不接受"很多同学反映"             | "30 份问卷中 23 人提到"才算证据                |
| **删掉后要说得出损失** | 说不出用户损失什么，就是伪需求             | "要有已读功能"——这是药名，不是病名             |

## 五、常见错误对照

| 你写的                 | 问题         | 改成                                                 |
| ---------------------- | ------------ | ---------------------------------------------------- |
| "要有搜索功能"         | 功能不是需求 | "我想按活动类型和时间筛，以便快速找到能参加的那几个" |
| "响应要快"             | 无法验收     | "2 秒内列出结果"                                     |
| "很多同学都说约不到人" | 不是证据     | "S05 Q05：图书馆写作业时想出去玩，没找到人"          |
| "用户需要已读回执"     | 把方案当需求 | "我想知道申请是否已送达，以便决定要不要换渠道再问"   |
| 三条故事一个意思       | 重复         | 合并成一条，其余注明"并入 US-xx"                     |

## 六、提交后还要做两件事

1. **Assign 自己**——检查点要求"责任到人"，没指派等于没交
2. **回填清单**——`doc/需求/用户故事清单.md` 的状态列改成 `已核对·你的名字`，建完 Issue 再补 Issue 号：`已入库 #12`
